# Setlist Lab

ライブのセットリストを公演横断で分析し、傾向を掴んだうえで自分の予想セトリを組めるアプリ。
参加記録も残せる。スマホから GitHub Pages 上で使うことを想定した、ビルド工程なしの静的サイト。

初回起動時はサンプルデータ（架空のアーティスト）が入っているので、
APIキーが無い状態でも全機能を触って確認できる。

---

## できること

| | |
|---|---|
| **公演** | アーティストを登録し、setlist.fm から公演とセトリを取り込む。ツアー別に一覧 |
| **比較** | 公演を最大6件まで横並び表示。全公演で披露された曲と、その日だけの曲を色分け |
| **分析** | 位置別の確率 / 曲のつながり / セトリの感情の起伏 |
| **マイセトリ** | 実績を見ながらセトリを組む。分析結果からの自動生成もできる |
| **記録** | 参加した公演に座席・同行者・メモ・評価を残す。「自分が生で見た曲」も集計 |
| **楽曲** | 30秒試聴をブラウザ内で解析して「激しさ」を算出。手動補正も可能 |

### 3種類の分析

**1. この位置に来やすい曲**
1曲目 / 本編ラスト / アンコール1曲目 / アンコールラスト を集計する。
確率は必ず「12公演中9回 (75%)」のように分母つきで出す。割合だけだと
「1公演中1回だから100%」を強い傾向と読み違えてしまうため。
アンコールが無い公演はアンコール系の分母から除外している。

**2. 曲のつながり**
曲を選ぶと「その次に来た曲」がランキングで出る。
さらに「ほぼ固定の流れ」を自動検出する。回数の少ない並び
（2回中2回で100%、など）は偶然と区別がつかないため、
信頼区間の下限が5割を超えるものだけを採用している。

**3. セットリストの感情の起伏**
曲ごとの「激しさ」を並べて、構成タイプを自動判定する。

- **ゾーン分離型** — 激しい曲とバラードがまとまって配置されている
- **交互型** — 激しい曲と静かな曲がほぼ1曲ずつ交互
- **右肩上がり / 山型** など

判定は連（ラン）検定による。中央値の上下で並びを見て、同じ側が続く回数が
偶然の並びより有意に少なければゾーン分離型、多ければ交互型とする。
「なんとなくの閾値」ではなく、偶然と比べて偏っているかで決めている。

## セットアップ

サンプルデータを触るだけなら設定は不要。実データを取り込むには次の2つが要る。

### 1. setlist.fm の APIキー（無料・非商用）

1. [setlist.fm](https://www.setlist.fm/signup) に無料登録
2. ログイン後 [APIキー申請ページ](https://www.setlist.fm/settings/apps) でアプリを登録
3. **キーはフォーム送信後すぐ発行される**（審査待ちがあるのはレート上限の引き上げ申請だけ）

標準キーの上限は **2リクエスト/秒・1440リクエスト/日**。

### 利用規約への対応

[API利用規約](https://www.setlist.fm/help/api-terms) の要件のうち、
実装で対応しているもの:

| 規約 | 対応 |
|---|---|
| データの保持は**短期キャッシュのみ** | 取得分は既定14日で自動破棄（設定で変更可）。Worker 側は6時間キャッシュ |
| データ表示箇所への**帰属表示が必須**、nofollow 禁止 | 公演/比較/分析/マイセトリ/記録の各画面に setlist.fm へのリンクを表示。`rel` は `noopener` のみ |
| **APIキーの第三者共有禁止** | キーは Worker の環境変数に秘匿。ブラウザには渡らない。Worker は Origin 許可リストで保護 |
| **非商用利用のみ** | 個人利用の想定 |

自動破棄で消えるのは setlist.fm から取得したセトリだけ。
手動入力のセトリ・参加記録・マイセトリは自分のデータなので残る。
参加記録には日付と会場の控えを持たせてあるので、
取得データが破棄されても「いつ・どこの公演だったか」は失われない。

### 2. Cloudflare Worker（中継サーバー）

setlist.fm の API は **CORS ヘッダーを一切返さない**（プリフライトも403）ため、
ブラウザから直接呼べない。同梱の `proxy-worker.js` を中継として置く。
APIキーは Worker 側に秘匿され、ブラウザには出ない。

1. [Cloudflare ダッシュボード](https://dash.cloudflare.com) → Workers & Pages → Create → Worker
   「Hello World」テンプレートで適当な名前を付けて Deploy
2. 「Edit code」で `proxy-worker.js` の中身を全部貼り付けて Deploy
3. Worker の **Settings → Variables and Secrets → Add**
   - **Type: `Secret`**（`Text` ではない。Secret にすると以後値は表示されなくなる）
   - 名前: **`SETLIST_KEY`** ／ 値: 取得したAPIキー
   - **Deploy を押す**（押さないと反映されない）
4. `proxy-worker.js` の `ALLOWED_ORIGINS` を自分の GitHub Pages の URL に書き換える
5. 発行された URL をアプリの **設定 → setlist.fm の取得サーバー** に貼って保存
   → 「接続を確認」でキーの設定状況まで確かめられる

疎通確認はコマンドラインからもできる（`hasKey: true` ならキーまで通っている）:

```sh
curl -s https://<name>.<sub>.workers.dev/health
# {"ok":true,"service":"setlist-lab-proxy","hasKey":true,...}
```

Git 連携は不要（リポジトリ権限を渡さずに済む）。

## ローカルで動かす

ES モジュールは `file://` では読み込めないので、HTTP で配信する。

```sh
node serve.js          # http://localhost:5175
node serve.js 8080     # ポート指定
```

起動時に LAN の URL も表示される。PC とスマホが同じ Wi-Fi にいれば、
その URL をスマホのブラウザで開いて実機確認できる。

## GitHub Pages への公開

```sh
git init
git add -A
git commit -m "Setlist Lab"
git remote add origin https://github.com/<user>/setlist-lab.git
git push -u origin main
```

GitHub のリポジトリ設定 → Pages → Source を `main` ブランチのルートにする。
ビルド工程は無いのでこれだけで動く（`.nojekyll` を同梱済み）。

公開後は `proxy-worker.js` の `ALLOWED_ORIGINS` にその URL を入れ、Worker を再Deploy する。

## データの取得元

| ソース | 用途 | CORS | 認証 |
|---|---|---|---|
| setlist.fm API | セトリ・公演情報 | **不可 → Worker 経由** | APIキー |
| MusicBrainz | アーティスト検索（MBID解決） | 可 | 不要（1req/秒） |
| iTunes Search API | 日本語曲名・ジャケット・試聴URL | 可（**iOSのみ Worker 経由**） | 不要 |
| iTunes 試聴音源 | Web Audio 解析の入力 | 可（iOSでもそのまま取れる） | 不要 |

### iTunes のレート制限（1IPあたり約20回/分）

制限が厳しいので、曲ごとに検索すると20曲でつまずく。そこで

1. アーティストの**楽曲カタログを1回だけ一括取得**（200曲まで＝リクエスト1回）
2. セトリの曲名を手元で照合
3. カタログで見つからない曲だけ個別検索（3.2秒間隔＝約18回/分）

としている。Official髭男dism（94曲）での実測では、カタログで40曲が解決し、
個別検索は54曲だった（従来の94回 → 56回）。残りは日本語タイトルの曲で、
setlist.fm ではローマ字（「宿命」→「Shukumei」）のため文字列では一致しない。
解析結果は端末に保存されるので、この待ち時間がかかるのは初回だけ。

429 が返った場合は15秒・30秒と待って自動で再試行する。

**Cloudflare Worker 経由では iTunes が 429 になりやすい**（外向きIPが他の利用者と
共有のため）。そのため iTunes は原則ブラウザから直接呼び、
直接呼べない iOS のときだけ Worker を経由する。

### iPhone / iPad での注意

iTunes Search API は **iOS の User-Agent に対して `musics://`（Music アプリへの
ディープリンク）へ 301 を返す**ため、iPhone・iPad のブラウザからは直接呼べない
（`fetch` が `ERR_FAILED` になる）。ブラウザからは User-Agent を差し替えられないので、
**iTunes の検索も Worker 経由**にしている（Worker はサーバー側なので影響を受けない）。

試聴音源そのもの（`audio-ssl.itunes.apple.com`）は iOS でも普通に取得できるため、
音声解析の本体は端末内で完結したままで、Worker には検索だけを通す。

Android・PC は Worker が無くても直接呼べるので、未設定なら直叩きにフォールバックする。

### 楽曲の特徴量について

Spotify の `audio-features` / `audio-analysis` は **2024年11月27日に廃止**され、
新規アプリからは利用できない。代わりに iTunes の30秒試聴を
**この端末のブラウザ内で解析**して特徴量を算出している（外部の解析APIに送らない）。

```
2048サンプル窓 / ホップ512 で自前FFT
  RMS                  → エネルギー、その分散 → 強弱の起伏
  スペクトル重心        → 明るさ
  スペクトラルフラックス → オンセット → 自己相関 → テンポ
      ↓ アーティスト内でパーセンタイル正規化して合成
  激しさスコア 0-100
```

再生はしないので `OfflineAudioContext` で完結し、
iOS の「音はユーザー操作から」という制約に触れない。

**既知の限界:**

- 30秒試聴はサビ付近が切り出されることが多く、静かな導入を持つバラードが
  高めに出ることがある。→ 「楽曲」画面の**手動補正**で直せる（手動値は再解析で上書きされない）
- テンポは 55〜210 BPM の範囲で合成信号に対し±1BPMの精度を確認済みだが、
  8分のハイハットが強い曲などでは倍のテンポに判定されることがある
- setlist.fm は**ラテン文字しか扱えない**ため、日本語タイトルの曲はローマ字表記で入っている。
  → 下記「曲名の正式名称化」で直す

## 曲名の正式名称化

setlist.fm はラテン文字しか扱えないため、日本語タイトルの曲はローマ字で登録されている
（「宿命」→「Shukumei」）。そのままだと画面がローマ字だらけで読めないので、
iTunes と照合して正式名称に直す。

**セトリの取り込みと同じ操作の中で最後まで直しきる。** ボタンを押し分ける必要はない。

```
「setlist.fm から取得」を1回押す
  ① セットリストを取得        10ページ / 約7秒
  ② 曲名を正式名称に直す
     ・楽曲カタログと照合      リクエスト2回 / 約7秒
     ・残りを個別検索          1曲3秒ほど（残り時間を表示）
```

途中で中止しても、そこまでに直した分は保存される。
残りは楽曲画面の「正式名称に直す」から続きを実行できる。

自動で直せなかった曲は、楽曲画面に**その場で手入力できる欄**が出る。
各曲の「調整」からも編集でき、元の表記に戻すこともできる。
手入力した名前は自動照合で上書きされない。

**設計上の要点として、集計キーは setlist.fm の原名から作ったものを使い続ける。**
正式名称をキーにすると、曲名を直すたびにキーが変わり、
解析済みの特徴量・参加記録・マイセトリとの対応が切れてしまう。
差し替えるのは表示だけなので、曲名を直しても分析結果は一切変わらない。

Official髭男dism（94曲）での実測: カタログ照合で40曲、個別検索で35曲が確定し、
19曲が手入力対象だった。うち30曲が日本語タイトルに直った
（残りは元から英語タイトルの曲）。

ライブ音源に当たった場合の「ブラザーズ (LIVE)」のような版の注記は自動で落とす。
ただし「Theme of Hi-Gumi ~Yamata-No-Orochi Edition~」のように曲名の一部である
括弧は残す。

## setlist.fm に無い公演

小規模ライブや、登録が追いついていない直近公演は手動で登録できる。
「公演 → ＋手動でセトリ追加」から入力するか、箇条書きテキストを貼り付けて取り込む
（「EN」「アンコール」などの行をアンコールの区切りとして自動判別する）。

手動登録した公演も、API 取得分と同じように分析・比較・参加記録の対象になる。

## 分析ロジックの自己検証

内蔵サンプルには「1曲目はこの曲が12公演中9回」といった**正解を意図的に仕込んである**。
**設定 → 分析ロジックの自己検証 → 検証を実行** で、集計結果がその正解と
一致するかをその場で確かめられる。数字を信用してよいかを自分の目で確認できる。

期待値は `js/sample-data.js` の `SAMPLE_FACTS` に書いてある。

## 構成

```
index.html            画面骨格
css/style.css         スマホ縦持ち基準。900px以上でサイドバー表示
js/
  main.js             起動・画面遷移・共有ステート
  store.js            localStorage 層
  api.js              setlist.fm(Worker経由) / iTunes / MusicBrainz
  normalize.js        setlist.fm JSON → 内部モデル、曲名の正規化と照合
  analyze.js          位置別確率・遷移・起伏判定・予想生成（純関数のみ）
  audio.js            Web Audio 特徴量抽出（FFT・重心・オンセット・テンポ）
  features.js         特徴量の解決と激しさの合成
  charts.js           SVG グラフ（コンテナ実寸で1:1描画）
  ui.js               DOM ヘルパー
  sample-data.js      内蔵サンプル＋仕込んだ正解
  views/              画面ごとの描画
proxy-worker.js       Cloudflare Worker（setlist.fm 中継）
serve.js              ローカル確認用サーバー（依存ゼロ）
sw.js                 Service Worker（アプリ本体のみキャッシュ）
```

データはすべて端末内の localStorage に保存される。
機種変更やブラウザのデータ削除の前に **設定 → バックアップを書き出す** を実行しておく。

## メモ

- 外部ライブラリ・ビルド工程なし。素の ES モジュールのみ
- 曲名や会場名は外部由来なので、`innerHTML` は使わず `textContent` で入れている
- ProtoPedia に掲載されている「LiveFans ライブ情報・セットリスト情報取得API」は
  **2018年3月26日に提供終了**しており、現在 LiveFans に公開APIは無い
